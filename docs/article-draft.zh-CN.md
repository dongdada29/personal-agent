# 让 Agent 接得住任务：一台电脑上的执行、接管与恢复

Personal Agent 的目标，是让个人电脑或虚拟机成为一个可以交付任务的执行节点：人在浏览器里描述目标，查看多个 Agent 的分工，在需要时处理审批、补充要求或接管执行，最后接收代码补丁和验证记录。手机远程操作是目标中的一部分，当前已经可以直接使用和复现的是本机工作台。固定 HTTPS 入口和真实手机跨网流程仍需后续配置与验收。

围绕这个目标，我们把完成标准落在具体行为上：任务创建后能找到记录；执行失败后能解释原因；页面关闭后进度仍在；服务重启时有证据判断哪些进程属于任务；接收成果时知道代码改了什么、测试实际跑了什么。这些细节决定了人能否放心把一个目标交出去，也决定了遇到问题时是否还能把控制权接回来。

工程采用 Node.js、TypeScript ESM 和 npm workspaces，服务使用 Fastify，工作台使用 React，任务记录保存在 SQLite。共享契约描述任务状态、事件、成果和控制命令，Runtime 负责调度、工作区、引擎与验证。当前一台机器运行一个实例，任务按先后排队，每次执行一个任务，分析阶段可以并行启动两个引擎会话。机器停机就无法访问，尚无服务冗余或自动故障切换。

第一次体验不需要模型账号。安装锁定依赖、构建后，可以启动一个独立的 fake 演示：

```sh
npm ci --ignore-scripts --registry=https://registry.npmjs.org --strict-ssl=true
npm run build
npm run doctor
npm run demo
```

终端会打印本机地址，默认是 `http://127.0.0.1:47811/?demo=fake`。演示使用新的临时数据目录，与正式实例端口分开，预置成功和故障任务。可以查看事件与成果，创建新的演示任务，再接收成果并刷新页面。按 Ctrl+C 正常关闭后，演示清理自己的临时数据。需要长期保留任务时，按 [首次运行说明](getting-started.md) 使用持久实例。

fake 是可控的协议与状态演示，不会照自然语言目标修改代码，也不调用模型。它有意保留故障入口，方便看到“执行失败”和后续正常任务。命令 `npm run demo -- --check` 会使用临时端口，检查真实 HTTP 创建、成功与失败路径、命令重放，以及 SQLite 与接口返回的状态、事件、成果是否一致，然后关闭并清理。界面能显示成功，与数据库中的记录能对得上，都需要验证。

真实开发任务从登记的 Git 仓库开始。创建任务时固定 HEAD，随后建立独立分支和 worktree。宿主目录的未提交修改不会自动带入任务，执行结果也不会直接覆盖宿主。这样，人在自己的仓库里进行中的工作可以保留，Agent 的补丁有明确基线。worktree 隔离的是 Git 修改；进程仍在本机运行，它不能充当操作系统安全沙箱，初次尝试应使用非敏感的专用仓库。

流水线先让 planner 和 reviewer 并行分析，再由 developer 开发，接着执行验证、审查和汇总。验证程序和参数由人明确指定，Runtime 使用参数数组实际启动命令，保存退出码和输出。模型写出“测试通过”，不会覆盖程序的失败结果。审查返回结构化结论；一次自动返工后仍未通过，或者审查结果不合法，任务就等待人处理，避免无限循环把决定推迟。

人在执行过程中有几种不同的介入方式。“阶段结束后暂停”让当前阶段先收尾；“立即接管”会停止当前阶段的 Agent 与验证进程，确认退出后进入暂停。接管保留工作区，人可以检查或修改代码，再继续未完成阶段。这里的接管指任务和代码层面的控制，尚未提供远程桌面或鼠标键盘接管。

补充要求会立即保存，默认从下一阶段生效。因此，在评审或汇总时新增代码要求，不会悄悄把流程退回开发；需要先接管处理，或者交付后填写要求退回返工。人工修改了 worktree 后继续，系统会重新验证和审查。验证证据关联完整补丁的指纹，旧的通过结果不能为新代码背书。

权限请求同样要留有可检查的内容。工作台展示工具输入、目标路径和 diff，人明确选择允许或拒绝。审批持续等待，页面离线不会变成自动批准；用户也可以直接暂停、接管或取消。审批属于当前执行尝试，任务结束或重启协调后，旧请求不能继续作用到新尝试。成果的“已完成”表示执行结束，“已接收”表示人认可交付，接收不会合并、提交、推送或部署代码。

浏览器操作还有一个容易忽略的问题：请求可能已经到达服务，但响应在网络中丢失。创建、控制和配置变更使用 commandId 标识一次意图，相同请求重试返回首次结果，避免一次点击变成两次执行。重新开始任务会产生新的 attempt，旧尝试迟到的消息和审批回执不能写入新尝试。重试得到什么结果、现在处于什么状态，分别由命令记录和最新快照回答。

SQLite 保存任务、事件、阶段、审批和控制意图，相关状态与事件在同一事务提交，提交后才通知订阅者。工作台先读取一致快照，再从其中的游标订阅 SSE。事件序号持久化，页面断线后可以补读遗漏；连接恢复期间也能使用轮询显示进度。关闭标签页只断开查看，不取消任务。用户真正希望停止时，应发送明确的任务控制命令。

服务重启涉及更难的一层：执行进程可能还在，保存的 PID 也可能已被其他进程复用。Runtime 使用独立 owner 进程组，先登记归属，再打开执行门禁。恢复时核验 Node executable、wrapper 路径、owner 标记和 PID/PGID，确认后才停止对应进程。证据不匹配、核验权限不足或收尾无法落库，就停止启动与调度，保留锁和账本供检查。

清理确认后，原活动任务进入 interrupted，旧审批过期。系统不自动重放原工具，人明确选择继续，才从持久检查点建立新 attempt。原先仍在排队的任务按队列调度。这种恢复保留执行上下文，也把重新执行的决定交给人；它不能消除停机时间，更不能保证所有外部操作天然可逆。

交付因此还需要运维说明。数据目录包含数据库、worktree 和归属记录，备份应在正常停机、执行进程收尾后进行。冷备份工具拒绝既有锁和未关闭的进程账本，不会为了复制数据结束服务或删除别人的锁。worktree 还依赖源仓库的 Git 对象与绝对路径，复制一个目录并不等于完成跨机器迁移。升级可能迁移数据库，代码回退要配套匹配的数据备份，具体步骤见 [运行维护](operations.md)。

关于“已经验证了什么”，需要把证据分层。fake 证明协议、状态和持久化路径；真实模型固定文本探针证明初始化、会话和一次认证模型往返；真实开发 fixture 才证明文件修改、实际测试与审查能够连起来。一个层次的通过不能代替另一个层次。

历史 [真实 fixture 验收](phase2-acceptance.md) 使用无第三方依赖的 greeting 仓库，基线三项测试有两项故意失败。Claude 在独立 worktree 修改 greeting 并新增 CHANGELOG，Runtime 最终实际得到三项通过，补丁和汇总可查看，宿主 README 的预置 WIP 保持原样。这是当时主机上的小型开发闭环，不能推定任意项目、任意 provider 或新机器都已验证。

2026 年 10 月 7 日，我们在本机完成了一次新的真实 greeting fixture：五个阶段、五次 AgentRun 均完成，Runtime 实际运行的三项测试通过，退出码为 0，产生八项成果。浏览器中接收后，刷新页面、重新选择原任务，成果仍能查看；临时服务正常重启后的快照也保持一致，原仓库的 WIP 没有改变。这次实测沿用本机既有认证，没有在恢复工作中重复发起有成本的真实任务。

同日从 `39fe311` 导出的干净源码在独立目录安装了锁定依赖，类型检查与构建成功，macOS arm64 / Node 24.18.0 的 33 个测试文件、605 项测试全部通过，没有跳过。doctor、smoke 和真实 HTTP fake demo 也成功。此前 10 月 6 日在 MacBook 两个 Node 版本与 M1 独立目录的三次 605 项回归属于历史证据，不能写成今天又验了三台环境；日期、源码和完整命令见 [交付验收记录](delivery-acceptance.md)。

恢复演练只用了自建 fake 实例。我们让独立 ACP 进程遇到一次瞬时故障，明确重试后任务完成；另一任务执行中杀掉自建服务，重新启动后任务进入 interrupted，保留旧事件，明确重试才建立新 attempt。正常停机后的冷备份逐文件校验通过，恢复副本里的完整任务快照与 accepted 状态保持一致，还能完成新的 fake 任务。这说明已验路径可恢复，不等于生产容灾；M1 正式实例没有参与故障注入或升级。

设备鉴权的自动测试使用临时数据库、虚拟设备和测试会话，覆盖同源、CSRF、过期与撤销；窄屏浏览器验收使用 390 像素视口，检查任务、审批和成果有没有横向溢出。这些证明代码与布局行为，不能称作真实手机移动网络验收。生产配对、HTTPS、固定域名和隧道还未完成，当前默认保持本机 loopback。手机关闭 Wi-Fi 后的下任务、审批、接管、重连、接收和撤销，需要后续逐项实测。
